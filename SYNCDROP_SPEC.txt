# SyncDrop — Agentic Coding Implementation Specification

**Document version:** 1.0  
**Project status:** Greenfield / implementation-ready specification  
**Primary goal:** Build a cross-platform desktop utility that lets a user right-click selected files or folders in a file manager and send them to a preconfigured synchronization target. Syncthing is the first synchronization backend, but the architecture must allow additional backends later.

---

## 1. Project Overview

### 1.1 Product name

**SyncDrop**

### 1.2 Product concept

SyncDrop is a desktop productivity utility that adds a **SyncDrop** contextual menu to supported file managers.

The user selects one or more files and/or directories, right-clicks, chooses:

```text
SyncDrop
    ├── Main Sync
    ├── Projects
    ├── Documents
    └── ...
```

SyncDrop copies or moves the selected items into the configured destination for the selected target.

The first release should **not dynamically create Syncthing folders**. Instead, each SyncDrop target points to a directory already configured as a Syncthing folder. Syncthing detects the resulting filesystem changes and performs synchronization.

This keeps the MVP reliable and makes SyncDrop independent from Syncthing's internal configuration.

### 1.3 Primary development environments

The project must be developed and tested on:

1. Fedora Linux 44 + MATE desktop — development machine; dual boots Windows 11.
2. Fedora Linux 44 + Xfce desktop.
3. Zorin OS 18 Pro — GNOME environment with both Nautilus/Files and Dolphin installed.

### 1.4 Linux file managers

The first Linux release must support:

1. **Thunar** — primary/preferred integration and first implementation target.
2. **Dolphin** — second integration target.
3. **Nautilus / GNOME Files** — third integration target.

This gives coverage across:
- GTK/Xfce
- Qt/KDE
- GTK/GNOME

Do not implement Cinnamon/Nemo, PCManFM, Caja, or other file managers in the initial release.

# 2. Design Principles

The implementation MUST follow these principles.

### 2.1 Core logic is file-manager independent

The actual SyncDrop engine must not contain Thunar-, Dolphin-, Nautilus-, or Windows-specific behavior.

File managers are adapters.

Architecture:

```text
                 ┌─────────────────────┐
                 │   Thunar Adapter    │
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │                     │
                 │    SyncDrop Core    │
                 │                     │
                 │ configuration       │
                 │ validation          │
                 │ copy/move            │
                 │ conflicts            │
                 │ history              │
                 │ logging              │
                 │                     │
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │ Sync Target /        │
                 │ Backend abstraction  │
                 └──────────┬──────────┘
                            │
                       Syncthing
```

### 2.2 No unnecessary Syncthing coupling

For MVP:

- SyncDrop does NOT need to modify Syncthing configuration.
- SyncDrop does NOT need to tell Syncthing to synchronize individual files.
- SyncDrop only writes to configured destination directories.
- Syncthing is responsible for detecting and synchronizing filesystem changes.

A Syncthing API integration may be added in a later release.

### 2.3 Cross-platform core

The core must work on Linux and Windows without platform-specific code being mixed into core modules.

Future macOS support should remain possible.

### 2.4 CLI-first architecture

The core functionality must be callable through a command-line interface.

Example:

```bash
syncdrop add --target main /home/user/test.txt
```

The file-manager integrations invoke this CLI or an equivalent stable local interface.

This makes debugging and automated testing much easier.

# 5. Configuration Model

MVP configuration example:

```json
{
  "version": 1,
  "targets": {
    "main": {
      "name": "Main Sync",
      "path": "~/SyncDrop",
      "backend": "syncthing"
    },
    "projects": {
      "name": "Projects",
      "path": "~/SyncDrop/Projects",
      "backend": "syncthing"
    },
    "documents": {
      "name": "Documents",
      "path": "~/SyncDrop/Documents",
      "backend": "syncthing"
    }
  },
  "defaults": {
    "operation": "copy",
    "target": "main",
    "conflict": "ask"
  }
}
```

## 5.1 Requirements

The configuration system MUST:

- support multiple named targets;
- support filesystem paths;
- support `~` expansion on Linux;
- support Windows user paths;
- validate target identifiers;
- reject duplicate target identifiers;
- reject invalid/missing destination paths where appropriate;
- preserve unknown future configuration fields when practical;
- have an explicit configuration schema/version.

## 5.2 Configuration location

Use platform-appropriate per-user configuration locations.

Linux should use an XDG-compatible location, for example:

```text
~/.config/syncdrop/
```

Windows should use an appropriate per-user application-data directory.

Do not require root/admin privileges for ordinary SyncDrop operation.

# 6. Core Data Model

Define interfaces/types approximately as follows.

```typescript
interface SyncTarget {
  id: string;
  name: string;
  path: string;
  backend: string;
}

type Operation = "copy" | "move";

type ConflictPolicy =
  | "ask"
  | "overwrite"
  | "skip"
  | "keep-both";

interface AddRequest {
  sources: string[];
  targetId: string;
  operation?: Operation;
  conflict?: ConflictPolicy;
}

interface OperationResult {
  success: boolean;
  source: string;
  destination?: string;
  operation: Operation;
  error?: string;
}
```

The implementation may refine these types but must preserve their conceptual responsibilities.

# 7. Core User Behavior

## 7.1 Copy file

Given:

```text
/home/user/Downloads/report.pdf
```

and target:

```text
/home/user/SyncDrop/Documents
```

result:

```text
/home/user/SyncDrop/Documents/report.pdf
```

## 7.2 Copy directory

Given:

```text
/home/user/Projects/MyApp
```

destination:

```text
/home/user/SyncDrop/Projects
```

result:

```text
/home/user/SyncDrop/Projects/MyApp
```

The directory itself must be preserved.

## 7.3 Multiple selection

Given:

```text
report.pdf
photo.jpg
invoice.xlsx
MyProject/
```

all selected together, the destination should contain:

```text
target/
├── report.pdf
├── photo.jpg
├── invoice.xlsx
└── MyProject/
```

## 7.4 Do not flatten directories

Never transform:

```text
MyProject/
  src/
  package.json
```

into:

```text
target/
  src/
  package.json
```

unless the user explicitly selected the contents rather than `MyProject` itself.

# 8. Conflict Handling

MVP MUST NOT silently overwrite existing files.

Supported policies:

```text
ask
overwrite
skip
keep-both
```

Default:

```text
ask
```

For CLI use, `ask` should only be used when an interactive terminal is available. Otherwise the CLI must fail safely with a useful error or require an explicit conflict policy.

"Keep both" must produce a deterministic non-destructive filename.

Example:

```text
report.pdf
report (1).pdf
report (2).pdf
```

The algorithm must avoid overwriting an existing file.

---

# 9. Safety Requirements

The application MUST:

1. Never delete the source during a `copy`.
2. Never overwrite existing data silently.
3. Validate source paths.
4. Validate destination paths.
5. Prevent accidental recursive copy into itself.

Example:

```text
source:
~/SyncDrop/Projects/MyApp

target:
~/SyncDrop/Projects
```

must not result in:

```text
MyApp/MyApp/MyApp/...
```

The application must detect when a destination is the source itself or is inside the source tree.

5. Use clear error reporting.
6. Never require administrator/root privileges for normal operations.

---

# 10. Move Operation

Move support is part of the core design but may be disabled in the initial context menu until copy functionality is proven.

A move means:

```text
source
   ↓
destination
```

with successful source removal only after the destination operation succeeds.

Cross-filesystem moves may require copy-then-delete semantics.

The implementation must never delete the source if the copy failed.

---

# 11. History

SyncDrop should maintain an operation history.

MVP history can be JSON.

Example:

```json
{
  "timestamp": "2026-09-23T14:00:00Z",
  "operation": "copy",
  "target": "projects",
  "source": "/home/user/Projects/MyApp",
  "destination": "/home/user/SyncDrop/Projects/MyApp",
  "success": true
}
```

History should eventually support:

- recent operations;
- source;
- destination;
- timestamp;
- operation;
- result;
- error information.

Do not implement "Undo" until the semantics are thoroughly defined.

---

# 12. Logging

Provide structured application logging.

At minimum support:

```text
debug
info
warn
error
```

CLI should provide a verbose/debug mode.

Example:

```bash
syncdrop --verbose add --target projects ./MyApp
```

Logs must never expose secrets such as Syncthing API keys.

# 13. CLI Specification

The CLI should support approximately:

```bash
syncdrop --help
syncdrop --version

syncdrop targets
syncdrop target list

syncdrop add --target main FILE...
syncdrop add --target projects FILE...
syncdrop add --target documents FILE...

syncdrop add --target projects --operation copy FILE...
syncdrop add --target projects --operation move FILE...

syncdrop config path
syncdrop history
```

The exact command parser may vary.

Exit codes must be meaningful.

At minimum:

```text
0 = success
1 = general operation failure
2 = invalid arguments
3 = configuration error
4 = conflict requiring user action
```

# 14. Thunar Integration — PRIMARY

Thunar is the preferred Linux file manager and MUST be implemented first.

The integration should use Thunar's supported custom action mechanism rather than modifying the SyncDrop core.

The adapter must provide context-menu entries that pass selected paths to SyncDrop.

The preferred user experience is:

```text
Right-click selection
    ↓
Send to SyncDrop
    ├── Main Sync
    ├── Projects
    ├── Documents
    └── ...
```

If Thunar's menu hierarchy makes a dynamic submenu impractical for the first implementation, begin with one top-level action:

```text
Add to SyncDrop
```

and allow the user to select a target through a CLI/UI prompt.

However, the architecture MUST leave room for a dynamic target submenu.

The Thunar integration must support:
- one file;
- multiple files;
- one directory;
- multiple directories;
- mixed files/directories.

The adapter must pass absolute paths where possible.

---

# 15. Dolphin Integration

Dolphin integration should use KDE's supported Service Menu mechanism.

The integration should be installed per-user where possible.

The service menu must accept selected files and directories.

Target actions should ultimately resemble:

```text
SyncDrop
    ├── Main Sync
    ├── Projects
    ├── Documents
    └── ...
```

The implementation must not put core copy/move logic inside the `.desktop` service-menu definition.

The service menu should invoke the SyncDrop CLI.

---

# 16. Nautilus / GNOME Files Integration

Nautilus is the third Linux file manager target.

Use Nautilus's supported extension mechanism rather than modifying GNOME Files itself.

The extension should:
- identify selected files;
- identify selected directories;
- expose SyncDrop actions;
- invoke the SyncDrop core/CLI;
- remain independent of Syncthing.

The initial Nautilus implementation may provide a single action:

```text
SyncDrop → Add to SyncDrop
```

with target selection handled by SyncDrop.

Later, dynamically generated targets may be exposed.

---

# 17. File Manager Adapter Interface

Create an abstract concept similar to:

```typescript
interface FileManagerAdapter {
  name: string;

  install(): Promise<void>;

  uninstall(): Promise<void>;

  isSupported(): Promise<boolean>;
}
```

The exact interface may change.

The important architectural rule is:

**File-manager adapters must not contain copy/move/business logic.**

They only translate:

```text
file manager selection
```

into:

```text
SyncDrop request
```

# 18. Syncthing Backend

The initial Syncthing backend is intentionally simple.

A target like:

```json
{
  "id": "projects",
  "name": "Projects",
  "path": "~/SyncDrop/Projects",
  "backend": "syncthing"
}
```

means:

> The directory is expected to already be managed by Syncthing.

SyncDrop then performs normal filesystem operations.

### MVP Syncthing behavior

SyncDrop must NOT:
- modify Syncthing's configuration;
- store Syncthing API credentials;
- start/stop Syncthing;
- assume a specific Syncthing GUI port;
- assume Syncthing is installed.

It simply writes to the target.

### Future Syncthing API integration

A later version may:
- detect Syncthing;
- query status;
- rescan folders;
- create/remove Syncthing folders;
- show connected devices;
- report synchronization state.

This must be implemented behind the backend abstraction.

Any coding agent working on this repository MUST:

1. Read this specification before modifying code.
2. Inspect the existing repository before creating files.
3. Never replace working functionality without testing it.

5. Add automated tests for non-trivial core behavior.

7. Do not add Syncthing API integration during the MVP unless explicitly requested.
8. Do not introduce a database unless explicitly justified.

12. Preserve directory structure.

# 36. Important Architectural Decision

The project should NOT be described as:

> "A Syncthing context-menu extension."

It should be described as:

> **"A cross-platform file-to-sync-target utility with file-manager integrations."**

Syncthing is the first backend.

This distinction is intentional.

The long-term product should allow:

```text
                 SyncDrop
                    │
        ┌───────────┼────────────┐
        │           │            │
    Syncthing   SyncDrop     Future
                Sync Engine   Backend
```

This preserves the option to build a custom synchronization engine later without throwing away the application.

# 39. Non-Goals for Version 0.1

Do NOT implement:

- cloud storage;
- account systems;
- authentication;
- remote server;
- custom synchronization protocol;
- file encryption;
- compression;
- deduplication;
- database;
- automatic conflict merging;
- real-time sync monitoring;
- Windows shell extension;
- macOS Finder extension;
- mobile application;
- automatic updater;
- telemetry.

The first objective is simply:

**Select → Right click → SyncDrop → Target → File appears in synchronized folder.**

Everything else comes afterward.
